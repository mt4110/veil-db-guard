## 主な指摘と反映

| 指摘 | 反映 |
| --- | --- |
| 観測できた要求だけを集計すると、負例未実施でもpassになり得る | バージョン付き固定profileと必須case/pathを先に展開し、不足をunknownとして残す |
| DB認証で拒否された直接接続を、経路閉鎖と混同し得る | transport/TLS/DB認証を別観測にし、閉鎖要求でTCP到達したらfailにする |
| 自由文を含む設定の丸ごと保存が、秘密最小化と矛盾する | 正規化は選択フィールドのみ。入力専用説明文を保存/表示/hashから除外する |
| 複数runで変更不存在の完全な証明を要求すると通常の試験が完了できない | 短い試験区間・前後snapshot・実行記録による限定した整合性とし、運用者申告を分離する |
| baseline/障害/復旧/cleanupは意図的な構成変化を伴う | 同一状態の証拠群と、事前計画に基づくphase/epoch別評価の集約を分離する |
| verification_idだけでは必須負例の不足や反復を区別できない | 固定case_idとattempt_idを追加し、同じcaseの反復で他caseを充足しない |
| ローカル秘密非出力試験とAWS実証の到達条件が混ざる | V14を同一buildのローカル証拠として別扱いにし、最終profile評価を性能/片付け後へ揃える |

再確認では、上記に関する重大・中程度の未解消指摘はありませんでした。レビューで全欠陥の不存在を証明したとは扱いません。T01/T02/T07/T16等に残した対象依存の問いは未解決のまま、解決先を記載しています。

## 追加記録: 基幹設計C0

2026-11-02、GCPのフィジビリティ・CLI実機確認と撤収の後、ユーザー指定により追加試験を区切り、[基幹設計](core/README.md)を作成しました。以下は上記M0とは別の設計レビューです。

主担当は全体構成、初期profile、実装分割と文書統合を担当し、3担当がcontrol plane、data plane、security lifecycleを分担しました。文書の読み合わせでは次を揃えました。

| 指摘・論点 | 採用した内容 |
| --- | --- |
| 観測CLIが製品目的になりやすい | policyから保護経路の準備・切替・閉鎖・維持・失効・復旧までを主責務とし、観測を下位部品へ位置付ける |
| クラウド対応とDB対応が混ざる | DeploymentAdapterとEngineAdapterを二軸に分離。GCP PostgreSQL→AWS PostgreSQL→MySQLの順で展開する |
| Capabilityの実装有無と観測範囲の語彙が担当間で異なる | support / implementation / coverageの三軸に統一し、本番適格性や現在effect成立の代替にしない |
| DB別の内部lockだけでは共有IAM/SG/roleの変更が競合する | resource/managed fieldのconflict keyと安定順lease取得を定義。native CASなし・外部調整不能の共有field変更は停止する |
| アプリ切替とnative executorの実行責任が曖昧 | 初版は限定native executorと、運用者deploymentへのbinding/handoff。申告・受領と実効確認を分ける |
| 無停止導入を保証した表現になる | 停止・処理中断の影響を明示した段階移行へ修正し、driver/pool/配置の条件をbindingに残す |
| IAM反映とsession終了が混ざる | 新規接続・session・SQL権限・credentialを別効果とし、Pending中のAllowedを保持する |

共通設計の選択は揃えました。個別native stepの権限・payload、アプリの配置/driver/pool、対象ごとの管理・復旧経路、SQLite依存/migration等は[K作業](core/implementation-plan.md)で具体化します。追加フィジビリティを基幹着手の条件にはしません。

今回の設計ではコード変更、ビルド、製品試験、クラウド/API操作、課金を伴う作成、公開を行っていません。既存の試験・実機記録と証拠は保持し、未実装の基幹を実証済みとは扱いません。
