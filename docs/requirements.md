# 目的・要求・対象範囲

## 目的

既存の主要RDBMSを使うアプリの運用者が、DBを移し替えずに、正規接続を通し、不正・迂回接続から守る仕組みを導入・運用できるようにします。認証された接続経路の構築・導入・実接続確認をつなぎ、保護状態とその変化を追えることを目指します。初期AWS実装と追加GCP観測adapterに続き、[共通基幹](core/README.md)でポリシーから導入・維持・失効・復旧までをつなぎます。最初の基幹profileはGCP PostgreSQLです。

検証CLIの完成自体を最終目的にはしません。出力は、誰の接続を通し/止めたいか、現在どう接続できるか、保護成立が未確認なら何を確認すべきかという運用判断へつなぎます。権限の反映確認待ちでも現在接続できる事実を隠さず、保護済みと表示しません。

利用者価値の仮説は、IAM・TLS・ネットワーク・既存アプリの整合確認に必要な手順と見落としを減らすことです。利用者による有用性・導入負担・支払意思の検証は未実施です。OSS方針と将来の収益化判断は分けます。

## 構想と今回の対象

| 区分 | 内容 |
| --- | --- |
| I27・中心 | 正規アプリ→認証されたnative経路→既存RDBMS。許可していない主体・直接経路を制限し、必要な管理・復旧経路と限定DB権限を定義する。初期RDS構成から配置先とDBを分けて一般化する |
| I28・拡張 | 合成データと専用認証のみの隔離デコイ。本番への権限・接続経路を持たせない |
| I29・拡張 | 設定変更、迂回経路、デコイ通知の継続確認 |
| 初期の対象案 | 一つのAWSアカウント・リージョン・VPC内のRDS PostgreSQL、一つのRDS Proxy、一つの合成アプリ。具体的バージョンは実装前に固定する |
| 当初の継続実作業 | 設計に続きRust実装・fixture・新規loopback DBのローカル検証 |
| 追加承認済みの作業 | GCP実機フィジビリティ、直通/IAM拒否の追試、Veil CLIのGCP check/report実装・ローカル/実機検証、専用環境の撤収まで完了 |
| 基幹設計 | 追加試験を止め、共通ポリシー、二軸adapter、導入・維持・失効・復旧の基幹設計と実装作業分割を作成済み |
| 今回の継続実装 | K01/K02に続き、K03の差分・限定承認・復旧計画、K04のSQLite台帳・中断再開kernelを実装しローカル確認。native適用、追加フィジビリティ・クラウド操作は行わない |

初期の実装対象を限定しても、I28・I29と既存DB導入を消しません。M3のサンドボックス実証はM4の既存DB導入へつなぐ中間到達点です。

## 利用の流れ

1. 対象DB、アプリ、必要な管理経路、期待する認証方式と変更できない条件を定義する。
2. 明示した対象だけ構成を読み取り、不足情報と構築・変更計画を作る。
3. 変更内容・共有影響・復旧先を確認し、承認された範囲でnative機能から保護経路と限定権限を準備する。
4. 正規アプリ・pool・jobと管理経路を段階移行し、切替前に唯一の接続経路を閉じない。
5. 不要な直接経路と古い許可を閉じ、構成と接続状態を照合する。設定受付と保護成立を分ける。
6. 変更差分、反映待ち、例外、現在の接続状態を示し、承認済み範囲で維持・失効・復旧を行う。

この流れは次期基幹の目標です。現行CLIが変更・移行をすべて自動実行するという意味ではありません。

## 要求

| ID | 要求 | 完了を判断する証拠 |
| --- | --- | --- |
| R01 | 既存DBのデータ・スキーマを置換せず導入する | 既存DBを使うM4の導入・復旧記録 |
| R02 | AWS既存機能と自作部分を分け、構築計画を出せる | 計画に対象、差分、前提、変更・復旧手順がある |
| R03 | 正規アプリがProxy経由で必要なCRUDとトランザクションを実行できる | 実AWSでコミット/ロールバックと後条件を確認 |
| R04 | 認証なし・誤認証の接続を拒否する | 到達可能な同条件の正規接続と、期待する認証失敗 |
| R05 | アプリ等の許可していない接続元からDBへの直接接続を拒否する | 接続元と対象を固定した経路ごとの試験。管理例外は別記 |
| R06 | アプリ→ProxyとProxy→DBのTLSを区別して確認する | 各区間の設定・認証・接続証拠。片区間の結果で代用しない |
| R07 | トークン更新、新規接続、再接続、切断・障害後の復帰を扱う | 原因を区別した再接続試験。トークン期限とセッション寿命を区別 |
| R08 | 管理・バッチ・移行・復旧経路と権限を明示する | 許可行列と正規管理接続・失効/復旧の記録 |
| R09 | 構成の意図との差と、確認不能な情報を示す | 構成の差分、参照失敗、不足情報の報告 |
| R10 | 導入前後の性能・エラーを同条件で比較する | 入力/環境/測定方法を固定した生データと集計 |
| R11 | 証拠の環境・対象・時刻・範囲と不確実性を保存する | 構造化レポート。ローカルとAWSの証拠種別を保持 |
| R12 | 秘密と顧客データの取得・出力を最小化する | ダミー秘密値を使う漏出試験、ログ/成果物の確認 |
| R13 | 対象・並行数・期限・資源利用を制限し、中断後も結果を残す | タイムアウト/キャンセル/部分失敗試験 |
| R14 | 構成生成やモック試験だけで防御成立と判定しない | 証拠不足・古い証拠・失敗原因不明の判定試験 |
| R15 | 隔離デコイと通知の検証へ拡張できる | 将来M5で隔離・疑似侵入・通知の独立した実証 |
| R16 | 継続確認で環境・条件・例外の変化を扱う | 将来M5で比較可能性、ドリフト、通知状態の検証 |
| R17 | 導入を変更前にレビューでき、復旧できる | サンドボックス/既存DBそれぞれの変更・復旧計画 |
| R18 | 運用者が導入・確認・次の対応を判断できる | M4で利用者に手順を試してもらう。価値判断は技術合格と別記 |

## 初期版で前提にしないもの

新DBエンジン、新暗号方式、汎用SQLプロキシの自作、SQLごとの認可、正規アプリ侵害時の全操作防止、全接続元からの経路不存在の自動証明は対象にしません。認証トークンの期限を既存セッションの強制終了として扱いません。

## 成功条件の扱い

マイルストーンごとに [milestones.md](milestones.md) の条件で評価します。M1の契約・ローカル試験、M3のAWSサンドボックス、M4の既存DB導入は別の達成です。新しい条件が必要になった場合、変更理由と影響を記録し、過去の達成を後から失敗へ変更しません。
