# 接続保護のセキュリティとライフサイクル

更新: K06の初期lifecycleに続き、K07/K08でAWS PG／MySQLの限定実装を追加しました。[K06の実装と制限](k06-lifecycle.md)と[K01〜K08の設計照合・残作業](design-implementation-audit.md)を参照します。以下は全体設計で、すべてのexecutorが揃ったという意味ではありません。実環境の適用は行っていません。

設計: 既存の主要RDBMSを置き換えず、正規アプリの接続と必要な業務操作を維持しながら、許可していない認証主体・直接経路・管理経路を制限する基幹機能を定義します。この文書は構築・変更操作の実装や実環境への適用を承認するものではありません。新たな試験・クラウド操作は行わず、既存の設計と観測から具体化しています。

通常のSQL通信、接続認証、DB権限、ネットワーク制限は、対象クラウド・DB・既存Proxy/Connectorのdata planeへ任せます。Veilが作るcontrol planeは、共通policy、導入・変更・失効・復旧の順序、操作権限、現在状態と残る不確実性を管理します。`gcp check/report`は観測・評価の一部です。変更lifecycleは限定範囲を実装済みで、補償・session・期限回収等は残っています。

## 1. 守る対象と信頼境界

| 境界 | 認証・認可の条件 | Veilの責務 |
| --- | --- | --- |
| 運用者・CI → control plane | 運用者のidentity、担当target、許可された操作、承認の有効範囲 | 観測者、計画者、承認者、変更実行者の権限を分ける。同一人で兼務する初期運用でも、読取資格情報から変更権限を暗黙に取得しない |
| control plane → cloud/DB管理API | 明示targetに対する読取・変更権限 | 対象とpolicy revision、変更前条件、操作範囲を照合し、adapterが持つ限定操作だけを呼ぶ |
| アプリ → 正規Proxy/Connector | workload identity、許可された実行元、当該区間のTLS/ローカルIPC条件 | アプリと経路をpolicyへ対応付ける。利用者入力の単なる名称をidentityの証拠にしない |
| Proxy/Connector → 既存DB | 当該区間のTLS、接続主体、DBログインとDB内権限 | frontend主体とbackend主体の対応・共有範囲を保持する。片区間の成功で全区間を代用しない |
| 管理・バッチ・移行・復旧元 → DB | 用途別identity、接続元、経路、必要なDB権限 | アプリの例外へ混ぜず、誰が何のために利用できるかを明示する |
| 証拠・外部設定 → evaluator/plan | schema、target、版、時刻、取得元、参照整合 | 外部文字列を命令として実行しない。hashの整合性と、操作承認・取得元の真正性を区別する |

この設計で防ぐのは、policyが許可していない主体・経路による接続です。許可済みアプリの侵害後に、そのアプリが正規に持つ全SQL権限の悪用まで識別できるとはしません。アプリのDB権限も必要な範囲へ絞り、接続保護とDB内の操作権限を両方扱います。

DBのデータ、既存スキーマ、アプリの業務SQLを置換しません。必要な認証設定、接続先、DBログインrole・権限の追加/変更は、既存アプリ・管理経路との対応を計画に含めます。既存roleを広域に書き換える変更や、別アプリの接続を一緒に止める変更を隠しません。

## 2. 共通policyが表す接続契約

policyは最低限、target、workload/管理主体、接続元、経路、DBログイン主体、許可/拒否、TLS条件、管理例外、適用期間、変更可能な資源を結び付けます。対象には主要endpoint、別名・直接endpoint、利用するaddress familyと、Proxyを通らず接続できる経路を含めます。取得できない経路は未確認として残します。

認証情報の保有、接続認可、DBログイン、SQL権限は別です。短期tokenを発行できてもDBへ接続できるとは限らず、DBにログインできても業務操作に必要な権限があるとは限りません。逆に、SQL権限不足だけを接続拒否の達成には使いません。

共通policyを各providerへ変換する際、実装できない条件を弱い条件へ黙って変換しません。たとえばworkload単位の新規接続停止が必要なのに、共有backend user全体の停止しかできない場合は、その影響と非対応条件を示します。利用者が別の遮断範囲を選ぶ場合は、変更された契約として扱います。

通常アプリの常設許可と、一時的な管理・移行用のJIT許可は別のpolicyです。常設の正規アプリ許可を、controllerの定期更新が必須な短期leaseへ一律に置き換えません。JIT許可だけを指定した期間・効果で回収し、常設アプリの可用性と混同しません。

## 3. 三つの停止効果を分ける

| 要求する効果 | 意味 | 代用できないもの |
| --- | --- | --- |
| 新規接続の停止 | 指定主体・経路から、新しい認証・DBセッションを作れなくする | tokenの期限、APIの変更受付、既存セッション一覧が一度ゼロだったこと |
| 既存セッションの終了 | 指定範囲のfrontend/backendセッションを終了し、処理中の接続も継続させない | 新規ログイン権限の削除、接続元ルールの変更、既存資格情報の失効要求 |
| DB内権限の縮小 | 既存/新規セッションで利用できるDB操作を制限する | ネットワーク閉鎖やログイン拒否。既に開始した処理への効果も別に扱う |

接続プールが既存backendセッションを再利用する場合、「アプリからの新規要求」と「DBへの新規ログイン」は一致しません。adapterは、frontend接続、backend接続、DBセッションのどれに作用する操作かを明示します。接続を止めた後も残るプールを、新規ログインの拒否だけで終了済みにしません。

正常な移行・通常の退役では、まず新規接続を制限し、許可された既存処理をdrainします。緊急時にはdrain待ちより終了を優先できますが、トランザクション中断、業務エラー、共有接続への影響を操作結果に残します。

## 4. Capabilityと操作結果

各target adapterは、provider名だけでなく、engine/version、認証方式、Proxy/Connector方式、接続の共有範囲、実行資格情報を含めてcapabilityを返します。これは対応を主張できる範囲であり、今回の操作が成功したこととは別です。

| Capabilityで示す内容 | 必須の説明 |
| --- | --- |
| 新規接続停止 | 対象粒度、使うnative制御、反映が非同期か、既存接続に効くか、反映上限が確認できるか |
| session識別・drain・終了 | frontend/backendの区別、対象を識別できる情報、終了権限、共有poolの影響、列挙の網羅範囲 |
| 期限付き許可 | 期限をdata planeが強制するか、controllerの後続操作が必要か、時計と期限の意味 |
| TLS・identity対応 | 各区間、CA/名前検証、主体変換、同一OS上のIPC・loopbackの保護条件 |
| 復旧 | 取り消せる構成、再発行が必要な資格情報、復元できないセッション/処理、必要な管理経路 |

未確認と非対応を区別し、固定値の「即時失効」や、根拠のない最大反映秒数を作りません。native機能が提供しない強制力を、control planeの状態名で補いません。

操作記録は、要求、実行、観測を別の軸で持ちます。具体的な型名はcontrol plane設計へ合わせます。

- 要求: target、policy revision、主体/経路/セッション範囲、要求する停止効果、許容する業務影響、期限、復旧先。
- 実行: 未実行、provider受付、設定反映、部分完了、失敗、中断、結果照合待ち。外部操作IDと、実行済みstepを対応付ける。
- 観測: 新規接続はAllowed/Denied/Unknown、既存セッションは残存確認/対象範囲内で終了確認/未確認。観測時刻と対象範囲を必ず持つ。
- 残課題: 未反映、共有pool、未取得経路、管理例外、既存セッション残存、手動対応の必要性。

たとえば「IAM変更を受け付けた。指定主体の新規接続は現在Allowed、反映確認待ち。既存セッションは未終了」と報告します。Pendingは既知のAllowedを消す状態ではなく、保護未成立のまま次の対応を示す補足です。

## 5. 期限・失効・反映待ち

tokenの認証期限、許可policyの期限、新規ログイン権限の失効、既存セッションの寿命を分けます。tokenが期限切れでも、既に成立したセッションが同時に終わるとはしません。control planeが停止しても期限を守る必要がある許可は、data plane側で強制できる方式だけをその条件で提供します。

controllerが期限後に権限を削除する方式は、「期限を過ぎたら削除操作を開始する許可」です。data planeによる期限強制と区別し、停止・資格情報不足・API障害で遅れる可能性を残します。必要な失効特性を満たせない場合、短期許可として無条件に採用せず、別のnative制御や対象範囲を選びます。

GCPの[追試](../gcp-rejection-validation.md#権限削除は即時遮断ではない)では、project policyから権限が消えた後も、新しいtoken・Proxy・SQL接続でログイン成功が残り、成功と拒否が混在しました。[製品CLI実測](../gcp-cli.md)でも、権限削除後のAllowedをPendingとして保持し、その後のIAMログイン層拒否へ移る結果を記録しています。このため、policyを再読して削除が見えたことを、新規接続停止の完了にはしません。

反映待ちでは、同じtarget・主体・権限層について、変更前構成、変更要求、変更後構成、現在の接続状態を結び付けます。宣言した削除だけではPendingの根拠にせず、別経路・別権限の失敗で穴埋めしません。有限の操作期限に達したら「遮断未確認/現在Allowed/実行済み変更」を保持して操作を終了し、既存権限を自動で戻しません。より強い停止が必要なら、緊急遮断として別の効果と影響を選びます。

連続拒否は観測履歴として残せますが、その回数で即時失効、将来の安定拒否、全経路の閉鎖を保証しません。取消しも、既にproviderへ受け付けられた変更を取り消したこととは別です。

## 6. 通常導入・移行・rollback

以下は既存DBへ保護を導入する順序です。DB複製やデータ移送を必須にしません。各stepの実行方法と必要権限はadapter/targetの計画へ落とします。今回の設計作業では実行しません。

| 段階 | 変更と正常動作の維持 | 次へ進む条件・停止時の扱い |
| --- | --- | --- |
| 現状の固定 | 正規アプリ、DB/Proxy、直接経路、管理/バッチ、認証/TLS、poolと共有roleを整理する | 既存の接続契約と変更可能範囲を特定。未取得を安全と推定しない |
| 保護経路の準備 | 新しいProxy/Connector経路、認証・限定DB権限、TLSを既存経路と並存させる | 正規アプリが必要な接続・業務動作を行う条件、復旧経路、変更前構成を計画に含める |
| アプリの段階移行 | 対象アプリの接続先/認証設定を切り替え、pool更新と既存処理のdrainを扱う | 正規経路が利用可能であることを確認する前に、既存アプリの唯一の経路を閉じない。並存中の直接経路は残る露出として表示する |
| 迂回経路の閉鎖 | 宣言した管理例外を残し、不要な直接接続・古いidentityの許可を閉じる | 実構成と現在の接続状態を照合。未反映・残存sessionを完了扱いしない |
| 運用状態へ移行 | policy revisionと実構成を対応付け、変更差分・例外・未確認を継続管理する | 適用完了と、すべての安全性の証明を分ける |

接続契約には、既存アプリのトランザクション、session設定、接続再利用、認証更新、バッチ/移行処理への影響も含めます。共有poolやbackend主体変換で意味が変わる場合、接続先の変更だけで互換と判断しません。

rollbackは変更前snapshotをそのまま全体へ上書きする処理ではありません。operationが所有し、実行した差分だけを対象にし、他の運用者/IaCによる変更を上書きしません。変更前条件に合わない場合は部分完了と残存状態を示し、安全な復旧stepへ切り替えます。

正規アプリの障害時は、まず保護経路内の設定/権限を直すか、事前に定義した管理・復旧経路を利用します。古い直接経路を開くrollbackが必要なら、戻る保護水準、対象元・期間・回収操作を明示します。可用性回復のために全体公開や全権限付与を暗黙選択しません。既存セッションの終了や中断したトランザクションは、構成rollbackで元へ戻せないことも示します。

## 7. 管理・復旧経路

管理、バックアップ、バッチ、移行、緊急復旧は、それぞれ対象主体・接続元・DB権限・利用期間を持つpolicy例外です。アプリidentityに管理権限を加えて代用せず、直接DB管理が必要なら、その経路が閉鎖対象外であることを明示します。

復旧には、control plane自身に依存しないnative管理手順を用意します。専用管理identity、接続元、秘密の保管場所、必要権限、障害時の担当、復旧後に閉じる例外を計画へ含めます。常時公開の万能管理入口を作ることを復旧条件にはしません。

緊急identityと資格情報は通常のアプリ・観測者から分離します。通常は操作権限を持たない担当が、事前に承認された条件・時間内で取得する場合も、実行targetと操作を記録します。承認・資格情報を取得できない状況では、操作不能を示し、認証の迂回で復旧したことにはしません。

管理例外を実際に利用した後は、発行した資格情報、変更した経路、残るsessionをそれぞれ回収します。例外の期限切れだけで既存sessionを終了したとは扱いません。

## 8. 緊急遮断

緊急遮断は「指定範囲の新規接続停止」と「既存session終了」を独立に要求できる操作です。target単位、workload単位、主体単位のどこまで可能かをcapabilityで決めます。共有identity/poolで対象アプリだけを識別できない場合は、影響が広がる範囲を先に示します。

1. 対象identityと経路を特定し、通常の失効、nativeのネットワーク/Proxy接続制限、DB側制御から、要求する効果を持つ手段を選ぶ。
2. 新規接続の制限を要求する。IAM変更の受付やネットワーク設定変更だけで即時遮断成功にしない。statefulな接続が継続する可能性もcapabilityに含める。
3. 必要なら、識別できた既存sessionをnative機能で終了する。共有backendへの影響と処理中断を記録する。新規接続を制限せずsession終了だけを繰り返して復帰を防いだことにしない。
4. 効果、未反映、対象外管理経路、未取得session、失敗stepを分けて返す。反映待ち・部分失敗でも、実行済みの制限を自動解除しない。
5. 復帰は別operationとして、正規経路を戻す対象と順序を決める。漏えいが疑われる資格情報を再利用して単に権限を戻さない。

sessionの列挙・終了は、対象DBとidentity対応、必要なら接続/開始時刻等の条件を再照合して行います。汎用の全session終了、SQL本文や顧客行の収集を既定操作にしません。列挙不能、shared poolによる帰属不能、終了権限不足の場合は「既存session終了は未対応/未確認」と返し、新規接続停止だけが完了したことを説明します。

## 9. Control plane停止・外部障害・再開

| 状況 | 必要な動作 |
| --- | --- |
| controller/CLI停止 | native data planeの既存policyと正規通信を維持する。controllerのheartbeat消失を理由に直接経路を自動開放しない |
| controllerによる認証更新が止まる | 初期構成では通常のtoken更新・接続poolをnative Connector/アプリ側が扱う。controllerがSQL通信や全接続の必須依存にならない |
| provider管理API停止 | 現data planeはそのnative動作を継続。構成・効果の再読不能はUnknown。確認できない変更や自動rollbackを推測実行しない |
| 許可期限が到来 | data plane強制の期限か、controllerによる後続回収かを区別。後者でcontrollerが停止した場合は未回収が残り得る |
| 適用途中のcontroller停止 | 再開時にoperation journalとprovider操作ID、現在構成を照合。未受付/実行中/適用済み/不明を区別して次stepを選ぶ |
| 正規data plane障害 | 想定した管理・復旧経路とnative運用手順を使う。controllerの判断だけで認証/TLSを無効化しない |

一つのtargetへの変更operationは直列化し、policy revisionと変更前条件をstepごとに確認します。外部運用/IaCとの競合も現構成の差分として検出し、古い計画の再実行を止めます。CLIを中断してもprovider側operationが続く場合、journalに「照合待ち」を残します。再実行はstepの所有範囲と現在状態を確認し、二重作成・再開放・他資源の削除を避けます。

初版はCLI orchestratorとtransactionalなローカル`OperationStore`を用いる設計とし、journalはimmutableな観測証拠の保管先と分けます。内部のtarget leaseはVeilの操作同士を直列化するもので、外部consoleや別のIaCを排他できるものではありません。常駐agentは通常のSQL通信や常設許可の必須要素にせず、期限後の回収を担うreconcilerが必要な構成では、その依存を個別に示します。

operation journalには対象、revision、承認範囲、期限、step結果、provider参照、観測、復旧先を保存します。ローカルのapproval receiptはoperatorが許可したscopeの記録であり、独立した承認者の認証や電子署名の代わりにはしません。token/password、SQL本文、顧客行は保存しません。実行時の資格情報は既存のnative資格情報取得を使い、Veil用証拠へ複製しません。利用するSDK自身の資格情報cacheと、Veilの記録非保存は区別します。

## 10. 初版の採用決定と具体化する条件

共通の方式選択は以下で固定します。追加フィジビリティ試験を今回の設計完了条件や基幹実装の開始条件にはしません。

| 項目 | 初版の採用決定 |
| --- | --- |
| 変更実行 | local-first CLIの限定native executorが、承認済みtyped stepを適用する。任意shell/SQL hookは設けない |
| 初期profile | `gcp-cloudsql-postgres-connector-v1`。専用workload identityと専用DB loginを対応付け、native接続認可・connector経路・DB権限を合成する |
| アプリ切替・pool drain・復帰 | 運用者の既存deploymentへのmanual handoff。Veilは秘密なしbinding、差分、実施条件と復旧先を渡し、受領と現在状態を別に記録する。アプリやruntimeの再起動コマンドを任意実行しない |
| session選択終了 | 新規接続停止と別capability。専用loginでもsession帰属・終了権限・対象粒度が不足する場合、要求を実行前に明示拒否し、他アプリを含む終了へ自動拡張しない |
| 管理・復旧 | アプリと独立したidentity・承認済みconnector経路・native管理手順・必要権限を必須plan項目にする。初期GCP profileではinstance全体のconnector必須化と矛盾する直接管理例外を残さない |
| 期限回収 | 常設アプリ許可とJIT許可を分離。native期限強制または明示reconcilerを持たない構成に、期限後の自動失効を保証しない |

実装時に具体化するのは、個別native stepのpayload/必要権限、アプリ配置・driver/pool、既存共有accountから専用loginへの移行差分、session帰属と許容中断、導入先ごとの独立復旧経路です。これは共通方式を選び直す未決ではなく、選択したtargetとbindingが満たすべき条件です。

要求する緊急遮断効果をnative機能で満たせない場合は`CapabilityGap`を返し、要求を弱めた操作へ自動変換しません。別の影響範囲や運用者の限定手順を選ぶ場合は、その効果と承認範囲を明示した計画へ戻します。

型とoperationの正本は[control plane](control-plane.md)、native契約とbindingは[data plane](data-plane.md)、実装順序は[基幹実装計画](implementation-plan.md)へ対応付けます。既存の実測範囲を越えた強制力や導入成功を、この設計だけで確認済みにはしません。
